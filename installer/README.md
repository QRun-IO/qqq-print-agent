# Machine installer

Build the service, AppKit companion and CLI into one x64 machine MSI:

```powershell
./build/Build-Installer.ps1
```

The version is `VersionPrefix` in `Directory.Build.props`; add `-ReleaseVersion X.Y.Z-rc.N` for a test build, whose numeric part must equal it. The build publishes self-contained .NET applications into a fresh per-run directory under `artifacts/package` and builds WiX 6.0.2 authoring. An explicit publish directory must not already exist; this prevents obsolete files from entering the harvested MSI. Existing reviewed outputs can be packaged using `-SkipPublish -PayloadDirectory <path>`; all component versions must match the requested release and source version. The resulting MSI is local development output and is **unsigned unless a signing certificate is explicitly provided**.

For a signing certificate already installed in the Windows certificate store:

```powershell
./build/Build-Installer.ps1 -CertificateThumbprint '<thumbprint>' -TimestampServer 'https://your-approved-timestamp-service'
```

Signing needs `signtool.exe` on PATH. The script signs the first-party executables before packaging and signs/verifies the resulting MSI. Stable releases are signed by the release workflow with Azure Artifact Signing instead; see [RELEASE-SIGNING.md](../docs/RELEASE-SIGNING.md). Never store signing secrets here.

Install the resulting MSI through an elevated Windows Installer session. It installs `QqqPrintAgent` as an automatic LocalSystem service, depends on the Windows Spooler, starts the service, and adds the companion to the Start menu. Configure and test printers accessible to LocalSystem; user-only network printer mappings are not sufficient. The current companion's management pipe requires local administrator access.

Customer branding uses this same MSI without a rebuild. Validate a deployment with PowerShell 7.4 or newer:

```powershell
./build/Install-Branded.ps1 -MsiPath 'C:\Deployment\QqqPrintAgent.msi' -BrandingFile './docs/branding.example.json' -WhatIf
```

Remove `-WhatIf` in an elevated administrator PowerShell to install. Optional `-ExpectedSHA256` verifies an approved release checksum first. The wrapper validates bounded JSON, 180-character customer/company labels, HTTPS support links and optional local PNG/ICO assets; it stages them under protected ProgramData and restores the previous configuration if MSI installation fails. It launches the standard `/i /passive /norestart` machine installation. The sample JSON needs no image files. The dry-run fixture `./build/Test-BrandedInstaller.ps1` validates inputs without requesting an installation and runs in CI after Verify.

`BRANDNAME` and `BRANDCOMPANY` public MSI properties set the service display name and installed-product labels. Their persisted HKLM values are reused by subsequent ordinary MSI upgrades, including updates installed from the companion. The installer creates a branded shortcut in the all-users **Print Connectors** Start menu folder; rename/full-uninstall cleanup verifies the exact owned target before deleting it. Optional ICO branding affects the AppKit application icon and this shortcut; embedded release binaries/icons remain shared. Internal service/AppId/MSI upgrade identity and paths stay fixed, and source/license attribution remains visible. See [Customer branding](../docs/BRANDING.md) for configuration precedence, rename/reset behavior and asset limits.

**A shortcut that another program holds (decided 2026-11-11).** The shortcut is created, renamed and removed by two required steps of the MSI (`--apply-branding` on install, upgrade and repair; `--remove-branding-shortcut` on a full uninstall), and Windows Installer undoes the whole run when a required step fails. A virus scanner, a backup or the Start menu can have a `.lnk` open for a moment, so these rules apply:

- A shortcut file that Windows reports as in use (a sharing violation or a lock violation) is tried nine times over two seconds. Access denied and other failures are not tried again.
- **An uninstall never fails over a shortcut file.** A recorded shortcut that is still held, or cannot be opened or deleted for another reason, is left where it is, and so is a held leftover temporary file (`.qqq-` and 32 hexadecimal digits, `.lnk`; a read-only one is removed). The registry record is removed all the same, because the product is leaving. A file that could not be opened was not judged to be ours and is therefore never deleted, and no deletion is scheduled for the next restart: an install before that restart would lose its new shortcut. What stays behind is a shortcut to a program that is gone; delete it by hand, or install again under the same display name, which takes it over. An install under another display name does not find it.
- **An untrusted Print Connectors folder no longer fails an uninstall either.** When the folder has an untrusted owner, lets an ordinary user write, or is reached through a link, nothing in it is opened, changed or deleted, and the uninstall goes on. The check exists so that an elevated process does not act on files an ordinary user could have put there; failing the uninstall on top of that protected nothing and kept the product installed. 1.2.1 and earlier 2.0 builds failed here.
- **An install, upgrade or repair is not failed by the product's own shortcut being held.** When the recorded shortcut under the display name being applied still cannot be opened or replaced after the two seconds, it is left exactly as it is and the run finishes; the registry record is kept, and the next install, upgrade or repair replaces it. The shortcut that stays starts the same companion: target, arguments and description are the same in 1.2.1 and in 2.0 (read in both), and the install path is fixed. Only a changed icon is missed until then. A previous display name's shortcut that is held stays for the moment and is removed by a later run.
- **What still fails.** An uninstall: the step does not run as an elevated administrator, the registry record under `HKLM\SOFTWARE\QRunIO\PrintAgent` cannot be changed, or the folder cannot be listed. An install, upgrade or repair, before anything is changed: the same first two; an untrusted install, Start menu or Print Connectors folder; a missing companion; a file under the wanted name that is not this product's shortcut, or that the registry does not record and that cannot be opened (it cannot be judged, so it is not overwritten: close the program that holds it and run the installer again); Windows' shortcut automation (the `WScript.Shell` object) not being available. Later: the new shortcut or the record cannot be written.
- **Where the reason is.** When one of these steps fails, Windows Installer shows only its general message that a program run as part of the setup did not finish as expected, and rolls back. The reason is in the service's activity log, `%ProgramData%\QqqPrintAgent\logs\qqq-print-agent-<date>.log` (readable by administrators; the folder survives an uninstall), in an error line that starts with `[Installer] Branding shortcut operation failed.` Each file that was left where it is has a warning line there that starts with `[Installer]` and gives the file name and the kind of the failure.

No real install, upgrade or uninstall has exercised these rules. They are shown by tests that hold real files open in temporary folders; the runs with an administrator are listed under "Qualify the upgrade from 1.2.x to 2.0" in [TODO](../docs/TODO.md).

The installer protects `%ProgramData%\QqqPrintAgent` for SYSTEM and Administrators and preserves the journal/enrollment through upgrades and uninstall. It replaces app/service/CLI together and stops the old service before removing files. Preserved credentials/data can be deliberately removed by an administrator after decommissioning; do not delete the journal while a device still has unresolved print jobs.

No inbound firewall rule or persistent privileged update daemon is installed. The companion uses AppKit update prompts with a machine MSI adapter: manual or optional startup checks use the fixed GitHub release feed, and installation requires confirmation and administrator rights. Protected staging and a copied CLI helper update all components together; completed stages/logs are retained for administrator review. Same-feed SHA-256 checks do not replace publisher signing. See [Updates](../docs/INSTALLATION.md#updates). Production release qualification must include signed installation, service-account printing while logged out, upgrade/reboot, and uninstall/reinstall recovery. Building an MSI alone does not establish those checks.

The installer suppresses MSI validator ICE03 because the bundled Microsoft WinUI `Microsoft.ui.xaml.dll`/`Microsoft.UI.Xaml.Phone.dll` have multi-language version resources longer than that validator's File.Language constraint, and their MUI resources include newer locale IDs absent from its static list. The vendor binaries are retained unchanged. ICE61 is also suppressed for intentional `AllowSameVersionUpgrades`, supporting RC-to-RC/stable releases that share a numeric MSI version. The app updater requires a strictly newer semantic release; manual MSI deployments must follow semantic release order and avoid downgrades. All other MSI validation remains enabled; installation and launch qualification are still required. See [ADR-0002](../docs/adr/0002-prerelease-quality-and-packaging.md).
