# Threat model: QQQ Print Agent

## Realtime boundary

The remote-control adapter accepts only inventory refresh and cancellation of one locally journaled spooler job. Desired pause/disconnect state is revisioned and persists by canonical server URL and device identity; older or conflicting revisions cannot resume a device. An independently processed authenticated WSS channel carries controls and receipts while documents stream over separate same-origin HTTPS requests. There is no job/control polling fallback. A paused device claims no new work. A disconnected device retains control traffic and in-flight receipts; already-submitted printing is not recalled. Reconnect is a transport refresh, never an OS or service restart. See [the realtime contract and operational limits](../REALTIME.md).

The native QQQ session adapter requires discovery before credentials and never treats a native control 404 as legacy permission. After support is negotiated, 404 does not remove restrictions. Authorization denial becomes authorization-required, without inferring that every 401/403 proves revocation. New claims wait for an authenticated, bound QQQ user and valid control state. Existing installations without a protected QQQ session wait for explicit sign-in; device proof alone cannot authorize normal service printing. The command line has no server transport: the `--legacy-compat` bearer diagnostics were removed in 2.0, and the code they used was deleted after them. No shipped code can send a device token outside a session. The printing API client takes no token and sets no Authorization header; it can be built only from a signed-in session, and every request it makes, a document download included, is sent through that session, which adds what authenticates it and refuses any address outside the printing extension's path. Inventory, job events and command receipts travel only over the authenticated realtime channel: with no channel they fail and are replayed after the reconnect, and nothing is sent over HTTP in their place. The command line keeps no credentials or journal of its own.

Printing has one path. A document reaches Windows only as a staged file whose length and SHA-256 were verified while it streamed: the worker hands the file's path to the print helper, which checks the file is a regular, absolute path and verifies its length and hash again before the spooler. The helper is the service's own executable started with `--printer-worker`, and it accepts three operations: discover printers, print a staged file by path, and cancel one spool job. A request is one line of at most 1 MiB characters (it holds a job's description and a path, a few kilobytes); the helper counts while it reads and refuses a longer one before it is held in memory. The service bounds the helper's answer at the same size, after reading it. The operation that carried a document inside the request, and the in-memory submission behind it, were deleted in 2.0, so no document travels in a message between the two processes.

The service stores only the QQQ session cookie and stable authoritative identity under service-identity DPAPI, and periodically resumes the standard session. Passwords stay in the companion; provider refresh/access tokens remain server-side. The companion holds a session only while a sign-in attempt runs: it discards its copy as soon as the service confirms that it took the session over, and also when a hand-over that was sent could not be confirmed, so the service is the only process that keeps one. CLI operations use the existing authenticated service pipe. The enrollment code reaches the CLI only through an environment variable or standard input, never as an argument, and the CLI prints it nowhere. Typed at a Windows console it is read without echo; redirected input is read as a line, and that includes a terminal that hands native programs a pipe instead of a console (the default Git Bash window, for example), where the terminal itself may echo what is typed and the variable should be used instead. An unattended caller with a console nobody types at must set the variable or redirect input, or the command waits. A command line the CLI refuses is never echoed, because it can carry a misplaced enrollment code or a sign-in callback address. The private browser callback is fixed and MSI-owned, forwarding bounded data only into an active same-user/session companion inbox after executable verification. It carries a short-lived authorization code, never a session cookie or PKCE verifier. Core validates exact advertised redirect, random state, PKCE and single-use expiry; when the server advertises `nonceValidation: REQUIRED` it also sends only that attempt's own authorization nonce as `expectedNonce` (never a callback-supplied or regenerated value) and refuses any other non-empty nonce policy; no callback creates an authentication attempt. Provider registration, installed callback delivery and long-duration renewal remain deployment qualifications.

Sign-out also ends the identity provider's browser session. The companion sends only the fixed registered callback with `sign-out`; the service refuses any other value, asks QQQ to log out with `nativeLogout.postLogoutRedirectUri`, and returns the provider end-session request to the companion over the administrator-only pipe. That request carries the provider's ID token hint (sensitive, bounded to 32 KiB, no whitespace or control characters), so it is never logged, the record prints redacted, and only the provider host is logged. Core refuses the data unless the issuer equals the one QQQ advertises, the end-session endpoint is HTTPS on the issuer's origin and identical to the provider's own discovery, and the callback is the one requested. The browser return is accepted only on the exact callback with the state this sign-out generated. Browser sign-in also sends `max_age=0` beside `prompt=login`.

Realtime frames and queues have administrator-configured byte/count bounds validated against declared client ceilings. Defaults are 1 MiB per complete frame, 64 queued frames and 4 MiB queued bytes. Fragmentation does not bypass the complete-message limit. The journal admits at most 4,096 command records and 128 retained connection states, failing closed when capacity is exhausted. A durable marker precedes any effect. Crash recovery produces OUTCOME_UNKNOWN; duplicate delivery reuses the exact saved receipt rather than repeating cancellation. No raw executable, printer name or arbitrary spool ID comes from the server: CANCEL_SPOOL resolves its job ID through the current connection's local receipt and verifies the exact QQQ document at the Windows spooler boundary.

Successful cancellation means Windows accepted the request, not that printed paper was recalled. Absent/completed jobs, ownership mismatch, failure, expiry and uncertain outcome remain distinct. Only a specific missing command receipt after expiry plus seven days retires its transport retry, preserving the exact local receipt and distinguishing retirement from server acknowledgement. Discovery/socket failures never use this exception. Acknowledged or transport-retired command history can be pruned after 30 days; unresolved current-connection evidence remains and causes explicit capacity backpressure. No global Windows queue purge is implemented.

## Claim boundary

A claimed job is untrusted input, and part of it is not even the server's. The options of a job are written by whoever submitted it and relayed by the server unchanged; the rest of the claim (identifiers, title, format, hash, length) is written by the server. The client therefore treats the whole claim as hostile and checks it before anything else handles it.

What is validated and bounded at the claim: the response is at most 2 MiB and is parsed to 1,024 levels of nesting; the job itself may nest to 64 levels counted from the response; job and printer identifiers are 1 to 200 ASCII letters, digits or `-`, `_`, `.`, `:`, so they are safe in a route and a log line (they are never used as file names, for which `:` would not be safe); the title is at most 1,024 code points; format and scale are tokens of at most 32 ASCII letters, digits or underscores; the content hash is 64 hexadecimal digits; the content length is 1 to 2,147,483,647; copies are 1 to 32,767; paper dimensions are complete, positive, at most 2,000 mm and never combined with a media profile. Creation time and status are only displayed and are blanked when missing or over-long. Fields the client does not read are ignored, as the contract requires of unknown fields. Text the client cannot read at all also fails these checks. The JSON parser accepts, as valid JSON, a surrogate escape without its partner (`\ud800` alone, `\udc00` alone, or the two the wrong way round) and bytes that are not UTF-8, and neither can be turned into text. A claim is refused when such text is a text member the client reads, or a member name in any object the client reads members from: the response beside the job, the job, its options or its media selection. Inside a field the client does not read it is ignored with the rest of that field. Whether a well-formed job may print (effective copies and size policy, the format the queue offers, the selected media still being current) is decided later by the worker, and the document is verified against the claimed length and SHA-256 while it streams.

A job that fails these checks but still names itself with one usable identifier is refused, not skipped: the worker records RECEIVED and then FAILED, delivers both, never downloads or submits the document, and goes on to the next job. The reason is fixed text chosen by the client ("The claimed job has no print options. No bytes were submitted."); nothing the server or the submitter supplied is repeated in it, so the reason of a refusal cannot carry text into the journal, the server's history or the companion. The refused job itself is recorded like any other: its title, up to 1,024 code points and otherwise unchecked, is kept in the stand-in, stored in the journal and shown in the companion's history, and its identifiers, format and creation time are kept when they pass the checks above. A title, printer identifier, format or creation time that cannot be read is left empty; nothing is substituted for it. A malformed replay of a job the journal already knows changes nothing.

The client matches member names without regard to letter case. A job that gives a member the client reads twice (in the job, its options or its media selection, for example `copies` and `Copies`) could therefore make the client act on a value the server did not mean, so such a job is refused as above. Names the client does not read may repeat freely, because nothing is decided from them.

Residual risk: a claim that cannot be identified cannot be refused. A response that is not JSON, is nested beyond 1,024 levels, names no usable job identifier (missing, malformed, or text that cannot be read), gives the identifier twice in the contract's spelling, or holds two job members names no single job; the lane stops with a logged error, the server offers the same job again on the next claim, and that device prints nothing further until the job is cancelled on the server. Of these only the nesting depends on a submitter. The parse depth of 1,024 is derived from the server's cap of 2,000 characters on a job's options: the server's JSON library sets no depth limit, the cheapest nesting (an array in an array) costs two characters a level, so about 1,000 levels fit in the cap, and the response, the job and the options object add three. A response nested past 1,024 therefore cannot be produced through the server's options cap as it stands. This closure rests on that cap: if the server raises it, or relays another submitter-controlled member, the depth must be revisited. The cloud queue preview is display only: it requires each entry to name its job and printer once with usable identifiers, tolerates members that are unknown or repeated, and prints nothing.

## Compatibility check

The connection wizard's check of a server runs before anyone has signed in, against an address an operator typed. It makes two public requests (discovery, then the sign-in description) and sends no credential with either: no session cookie, no device proof and no Authorization header, even when the client holds a session and a bound device. It follows no redirect. It never ends a held session, whatever the server answers; a 401 to one of its requests is reported as "asks for authorization" and the session is left alone, so a check cannot sign the service out. The caller's cancellation always wins over a failure that surfaces at the same moment.

Everything the check shows was sent by that unauthenticated server, so it is shown only in printable, bounded form: control characters, line and paragraph separators, bidirectional and zero-width format characters, private-use and unassigned code points become spaces, a value is cut at 80 UTF-16 units and never inside a surrogate pair, a problem's whole detail at 512, and the subject and issuer of a refused certificate at 512. The same applies to every line the session client logs that carries text from a response, a certificate or a browser callback: a value is cut at 80 units, longer text that an operator has to read or compare (an address, a listed callback, a principal, tenant or device identifier, an error description, a failure's message) at 512, and a server-supplied list at 32 values, so a server can neither forge a log line nor flood the log.

## Certificate exception

The development-only exception was one switch on the session client. Once on, that client accepted a certificate Windows does not trust from every host it contacted, which included the address the server gave for its sign-in provider's discovery document, wherever that was. It is now a set of at most two origins, fixed when the session client is built: the server's own, and the sign-in provider that server names. An untrusted certificate is accepted only for an HTTP request or a socket upgrade that is going to one of those origins. From any other host it is refused whatever the exception holds, the refusal is logged with the certificate and the origins the exception covers, and the compatibility check reports it. The set can be built only from well-formed HTTPS origins and cannot be widened afterwards. This closes the first half of audit finding C9. The second half stays open: the provider's discovery address is not yet required to be on the issuer's origin, so a discovery address on a third origin is now fetched under normal validation.

Where the two origins come from today. The service builds the exception from its saved setting and names the server's origin only. The companion's sign-in names the server's origin, reads the server's sign-in description under that, and, when the description names a provider on another origin, continues on a second session whose exception also names the provider, with a warning in the log naming both. The provider's origin is therefore taken from a server whose certificate was not verified, which is what the exception means for that server; it is not yet shown to the operator before it is used, recorded with the server, or held fixed when the server later names a different provider. Those are the multi-server steps that follow ([ADR-0004](../adr/0004-multi-server-runtime.md)): the service derives the provider's origin from its own read, stores it with the server, shows both origins in the warning, and never takes it from a client. Until then the service cannot prepare the provider's sign-out page when the provider has an untrusted certificate on another origin: the QQQ session is ended, the local sign-out completes, and the request fails at the provider's certificate.

The form of an origin. The provider's address is text the server wrote, and its origin is what an operator is shown before deciding to trust it. A host name can hold letters that look like others, characters that show as nothing and characters that end a line, so an origin is kept, compared and shown in one form only: scheme, the host's ASCII name and port. The ASCII name is the IDNA name the connection is really made to, so a look-alike letter appears as the `xn--` name it is, a zero-width character is not in the name, and a name written in Unicode and its `xn--` form are one origin, as they are for the session client's own same-origin rule. A host the platform cannot name in ASCII (one that holds a line or paragraph separator, or a name it does not treat as a domain name) is not an origin: it cannot be named in an exception, nothing covers it, the description's provider origin is reported as absent, and a certificate presented for it is refused with the host logged in printable form. The log line for every certificate decision names the host this way, because the address may be the provider's discovery address, which the server also wrote. So does every other line that names the provider's address: the grant that was accepted, the discovery document that is fetched and the request for it, what the provider answered, the authorization and end-session pages, and the companion's two lines for the page it opens in the browser. The host is formed for display in one place, and a described address is its scheme, that host, the port and the path, never a query, fragment or user information. Where such a line describes an address the server or its provider supplied as text, it says by kind what it left out ("(query omitted)") and never its content, which can be a secret; and a provider's authorization endpoint that is refused is refused by naming the rule it broke (it carries a query, it is on another origin), so the log alone says why an address that reads as usable was not used. The lines that reject a value quote it as it was written, made printable, because there the text itself is the point: an issuer that does not match another exactly (the provider's own against the one the server advertises, and the one a browser callback names against the one expected), and an issuer or a discovery address that fails the grant's checks, both in the log line that rejects the grant and in the compatibility problem an operator is shown. A host with a look-alike letter can therefore still appear as written in a rejection; it never does in a line that says what was accepted or used. A refused certificate is kept with the origin that presented it, in the same form, and the time on the session client's clock, so a caller can tell a refusal from the server from one from its provider; both are public information; the management contract's description of a refused certificate takes the address and the time from that record and accepts neither from a caller. The session client's same-origin rule is made on the same form: it refuses a request to another origin and holds a sign-in provider's authorization and end-session endpoints to the issuer's origin, and an address with no nameable origin is not the same origin as anything. Before, the platform's own exception for a host it cannot name escaped from those checks when a server put such a host in an issuer or an endpoint; it is now the ordinary refusal. The address of the provider's discovery document is the one such address the client connects to, and the platform throws when asked to connect to a host it cannot name. The grant is therefore usable only when its issuer and its discovery address each have an origin: otherwise sign-in and sign-out are refused as a configuration problem before any request for the provider is made, and a server check offers no browser sign-in. The server's own address is typed by the operator and is logged as typed where a line names the server; a line that describes a whole address (a request's route) names the host in the same ASCII form, and a line that says two addresses differ shows both in the form they were compared in (a request refused for another origin by the ASCII names, a saved session refused for another server as each was written).

## Data handling

The service owns `connection.dpapi`, `journal.db` and its WAL. The MSI retains state through uninstall/reinstall. Revoke/decommission the device and resolve pending jobs before deliberately deleting retained state. Only delivered terminal detail whose failures were reviewed is pruned; final-state evidence is retained. Never publish raw state or customer documents.

Service and companion persist serialized, credential-redacted AppKit logs with 30-day retention, rolling a day's file over to numbered segments at a configurable size (default 100 MiB, at most 10 segments kept per day) rather than suppressing entries; recent job snapshots come from durable connection-scoped metadata. Tray colors describe observed connectivity/queue state, not a guarantee of physical printer readiness or completed output.

## Follow-up

Qualify real in-app upgrades and broad hardware/driver behavior. The user accepts unsigned prereleases for now. Regression coverage includes interrupted jobs, credential recovery, retention, operator actions, bounded IPC and bounded child-process termination. Revisit this document when any network, privilege or persistence boundary changes.

Runtime branding is presentation-only, loaded from the existing administrator-restricted ProgramData directory. JSON size, text length, color syntax, HTTPS support links, and local PNG file size/dimensions are validated. No remote logo fetch occurs; malformed settings fall back to defaults. Machine identity, credentials and authorization are unaffected.

Sign-in startup requires an explicit administrator preference in the installed companion. The task uses that administrator's interactive identity and a fixed Program Files executable/arguments; it stores no password. Same-name foreign tasks are refused. Full uninstall deletes only exact owned definitions; upgrades preserve them. Device operator actions remain scoped to authenticated device jobs and approved/exposed printers; reprint creates a new job and requires duplicate-risk consent for uncertain/spooled originals.

## Machine-MSI updates: implemented source, installed acceptance pending

The current audit source gate passed **237 tests with zero warnings/errors**. The installed 0.1.7 companion passed all 16 desktop checks before this audit. The AppKit `IUpdateService` adapter, `UpdateCoordinator` integration, fixed-feed client and copied apply helper are implemented, but direct MSI upgrades and synthetic updater tests do not establish a successful real in-app update handoff. That qualification remains pending.

### Implemented flow and trust

1. The companion performs a user-requested check or an enabled startup check through AppKit's coordinator. Checking does not authorize installation; apply requires the coordinator's explicit offer/consent.
2. The release client queries the fixed `api.github.com/repos/QRun-IO/qqq-print-agent/releases?per_page=100` feed. Runtime customer branding, QQQ server address and user settings cannot replace this update authority.
3. The release client selects a newer eligible version, rejects releases below the minimum 0.1.3 baseline, ignores prereleases for stable installs and allows newer prerelease/stable versions for prerelease installs. It validates the repository release-asset path, version and expected filename, uses HTTPS and allows only expected GitHub/CDN redirects.
4. The release client bounds release metadata to 2 MiB, checksum text to 64 KiB and MSI content to 256 MiB. It writes a uniquely created partial file, validates SHA-256 against that release's `SHA256SUMS`, and only then renames to the staged MSI. Cancellation/failure cleans only the operation's own temporary file.
5. The adapter supplies a staging directory beneath the existing SYSTEM/administrator-restricted ProgramData tree. The client rejects a reparse-point staging folder; adapter/helper validation also checks relevant parent paths and rejects user-writable or substituted destinations. The update backend alone does not establish installed-build eligibility or ACL correctness.
6. A protected CLI apply helper, invoked with fixed structured arguments, revalidates the staged artifact immediately before applying one coherent MSI for service, companion and CLI. The helper's path, staging containment, checksum and release identity are validation boundaries, not assumptions derived solely from a prior UI check.
7. Windows Installer performs the machine update. Elevation stays explicit and subject to Windows/UAC and administrator policy. There is no persistent privileged update daemon, generic remote command endpoint, scheduled silent installer or UAC bypass. Canceling elevation leaves the existing installation and job evidence in place.

### Required update evidence

Unit/integration fixtures must cover fixed-origin/asset validation, channel/version policy, size/hash mismatch, redirect rejection, canceled download cleanup, reparse/untrusted path rejection and failed helper/apply outcomes. Installed acceptance must cover explicit UAC cancellation, blocked/in-use files, coherent version replacement, retained credentials/deduplication evidence, restart and Windows Installer reboot-required results. ### Apply-helper source checkpoint

`MsiUpdateInstaller` now copies the entire installed self-contained CLI into the protected update session's helper directory before handoff, avoiding a running helper's lock on product binaries. Source validation walks existing path components, rejects reparse points, checks trusted ownership and effective write ACLs (including generic write/all rights), and separately checks copied descendants. Normal inherit-only CREATOR OWNER rules do not count as direct write grants on the parent object.

The bounded request captures MSI hash/version and the exact parent companion PID/start time. The helper must be running from that staged copy, requires an administrator, and waits at most 30 seconds for the expected installed companion to exit; it never kills it. A verified MSI read handle disallows writes/deletion while Windows Installer runs. Installer arguments use structured `/i`, `/passive`, `/norestart` and a protected `/L*v` log path; the helper waits for Windows Installer without terminating it.

Exit 0 is accepted only when the actual installed companion ProductVersion matches the requested release, ignoring build metadata. Exit 3010 explicitly requires Windows restart and is not reported as fully active; cancellation and other failures are distinct. The helper atomically records a bounded, dated `updates/last-result.json`, writes the shared AppKit log, attempts to clear maintenance pause, and attempts to relaunch the fixed installed companion. The UI can read the last outcome after handoff, when the original coordinator no longer exists. If relaunch fails, protected result/install logs remain for diagnosis.

The runtime's update pause is bounded and keeps heartbeats alive; abandoned handoff does not permanently stop claims. Failed pre-handoff stages are cleaned by the adapter after path checks. Completed stages/helper copies/install logs are retained for administrator review; automatic update-stage retention is not claimed. Pure tests cover request/path/ACL/hash/exit/version policy without invoking an installer; the gate owner reported all 163 tests passing (36 Core + 127 Windows/CLI), locked restore and zero build warnings/errors. This includes synthetic helper tests, not real MSI application or installed UI acceptance.

### Metadata, history and deployment branding (0.1.5)

Local administrators can edit bounded device/printer presentation metadata through the existing protected management pipe. Physical queue identities and Windows destinations remain unchanged. Metadata is machine-local, synchronized under the existing scoped device credential, and displayed as text by the native QQQ UI. The management request limit is 64 Ki characters to accommodate JSON-escaped Unicode descriptions.

Job pages deserialize at most100 summaries, event delivery/recovery uses200-record batches and detail maintenance deletes at most250 eligible records per pass. Unacknowledged/uncertain evidence and deduplication summaries remain; this is bounded work per operation, not a bounded lifetime database. Diagnostic log clearing removes owned dated files only, with a shared write lock and reparse rejection; it cannot clear the print journal or credentials.

The optional branded-install wrapper requires an administrator, validates bounded local configuration/artwork and stages it under the protected service directory. The MSI uses public display-label properties and remembers them in HKLM; customer labels never select the executable, service identity, updater origin or privileged command. The shortcut helper validates fixed target/empty arguments/ownership before replacing or deleting a tracked shortcut. Customer artwork and strings do not change code-signing identity or source/license attribution. WhatIf validation and pure shortcut tests do not establish a completed branded MSI upgrade/rollback qualification.

Shared Start menu directories use a separate shortcut policy: deletion-only rights are allowed because they cannot create replacement content; untrusted writes, permission changes and ownership changes remain rejected. New shortcut folders have protected SYSTEM/Administrators full access and Users read/execute. Protected updater/data directories retain their stricter policy. MSI major-upgrade removal is now inside the install transaction; rollback behavior still requires installed qualification.

### Local peer and pre-existing machine state (0.1.8 audit)

Every management client authenticates the connected pipe's process against the installed SCM service PID, LocalSystem identity and fixed installed executable before transmitting request bytes. Retained service/process/token handles and repeated identity checks limit PID-reuse races. Clients request only explicit read/write rights with Anonymous impersonation; the runtime retains one protected first-instance pipe across requests. A substitute endpoint must receive no enrollment code or other command data.

Canonical machine state accepts only SYSTEM, Administrators and TrustedInstaller ownership and access grants. The initial validation covers existing descendants and rejects links, null DACLs and untrusted inherit-only grants. Existing hostile state is rejected rather than normalized and adopted. Store, log, branding, startup and updater entry points share the invariant; explicitly separate diagnostic directories remain outside machine-state adoption. Administrator changes after successful validation remain within the trusted boundary.

Direct MSI and branded installation enforce this invariant before using persisted files. The deferred preflight runs before folder creation; the installation script executes before old-product removal, which remains inside the rollback transaction. Startup definitions are created within validated state, then held against write/deletion while Task Scheduler reads them; the resulting definition is verified. Actual MSI formatting, component reuse, successful installed-peer authentication and hostile-tree rollback are separate native qualification requirements, not conclusions from unit tests.

### Explicit credential recovery

Unreadable session ciphertext is quarantined only on explicit sign-out or after fresh sign-in and authoritative binding succeed. Unreadable device proof remains in place until explicit enrollment replaces it; old journal scopes and local printer exposure are retained. Recovery never invents device authority or retries old print submissions. A missing readable session cannot be remotely revoked by local sign-out; the UI reports the separate QQQ revocation requirement. Background traffic remains fail closed.

Replacement pairing requires an explicit local setup choice and fresh standard QQQ authentication. Its persisted unbound identity prevents restoration from presenting old, revoked device proof. New claims remain gated until successful enrollment, binding and control synchronization. Default sign-in still requires the saved pairing's authoritative binding. Failed setup preserves old configuration; successful replacement changes journal scope without replaying prior-device work.

### Virtual development agent HTTP boundary

The virtual agent's native HTTP request helper rejects foreign origins before
attaching session or device credentials, refuses redirects, and sends the exact
configured Origin on unsafe cookie-authenticated requests. This preserves the
server's missing/foreign-Origin rejection. Discovery accepts canonical stable
three-part printing versions in major 2, matching the protocol fixtures.
Synthetic loopback HTTP tests cover these boundaries; they do not establish
production authentication, durable spooling or physical printing acceptance.
