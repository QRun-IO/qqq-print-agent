# Troubleshooting

| Symptom | Check |
| --- | --- |
| Companion cannot connect to service | Confirm the MSI is installed, `QqqPrintAgent` is running, and the companion is elevated. The command-line tool is only a client of that pipe; it does not host it. |
| Sign-in or discovery fails | Open **View logs**: every step (discovery, authentication metadata, native grant validation, provider discovery, browser callback, session verification by the service, device binding, identity check) is logged with the reason it stopped, and the dialog shows the same reason. Turn on **Debug logging** in Log settings for request routes, status codes, timings and realtime frames. |
| Sign-in works in the companion but "Service authorization not completed" | The service verifies the session itself as LocalSystem. A self-signed or private-authority certificate (for example a local Caddy root) that your user account trusts is not in the machine store, so the service's TLS check fails; the log shows `TLS certificate for host rejected: RemoteCertificateChainErrors`. Install the issuing root in **Local Machine → Trusted Root Certification Authorities**, or enter the server address and enable **Allow untrusted server certificate for this server** in Connection settings for a development server (the exception is bound to that one server). |
| Sign-out reports a failure on a development server with **Allow untrusted server certificate** on | The exception covers the server's own origin. During sign-in the companion also applies it to the sign-in provider the server names, but the service does not yet, so when that provider is on another origin with an untrusted certificate the service ends the QQQ session and signs out locally and then cannot read the provider's sign-out page; the log shows `TLS certificate for <provider host> rejected` and which origins the exception covers. The provider's browser session stays open: close the browser or sign out at the provider. Installing the provider's root in **Local Machine → Trusted Root Certification Authorities** removes the need for the exception. |
| Enrollment fails | Complete standard QQQ sign-in, then check the server URL, fresh/unconsumed code, device/facility configuration and server logs. Remote endpoints require HTTPS. The log records each enrollment step and the server's answer. |
| No printers in the service list | Install the queue for the machine/service identity. User-specific network mappings may not be visible to LocalSystem. Confirm Spooler is running. |
| Windows test page fails | Repair driver, connection or printer hardware locally before testing cloud printing. |
| Discovered printer never receives work | Share the queue locally, enable the matching discovered printer in QQQ and submit to that printer on the intended device. |
| Log shows "The printer inventory could not be read" | The line ends with the reason, and what to expect depends on the cause. **One printer's settings cannot be read:** its driver hangs (the read is given up after 20 seconds, and the reason is a timeout) or fails. Jobs for the other printers keep printing, unless dispatch is paused, the log has no "Print lane stopped", and only the printer list is not reported. Find the printer (open each queue's **Printer properties**; the one that hangs or errors is it), repair its driver or connection, or remove the queue from Windows. **The Spooler cannot list its printers, or the list stalls:** the reason is the Spooler's own error or again a timeout. The print lanes need the same list, so expect "Print lane stopped" in the log as well, and no printing for any printer until it is repaired (see the row on "Print lane stopped" below). **The service cannot read its own stored data:** the reason names the journal (a `SqliteException`, for example). The print lanes need the same data, so expect "Print lane stopped" as well, and no printing until it is repaired; check the disk and the service's data folder. In every case the server is told nothing new about any printer until it is over, a healthy one included. The line also says one of two things about the connection. "The inventory this connection already delivered stays in force" means that this failure by itself holds no job; whether jobs go on is decided by the cause, as above. "No job is claimed on this connection" means that the service restarted or reconnected while the list could not be read, and nothing prints until it can, whatever the cause. The log says "The printer inventory can be read again" when it is over. |
| Companion shows an error in place of the service's status, or `printers` / `snapshot` is slow and then fails with a timeout | The same cause: the snapshot the companion asks for carries the printer list, which reads every printer's settings. Jobs for other printers are not affected by it; see the row above. |
| No job is taken for any printer, and the log shows "Print lane stopped: The printer operation timed out" | The service could not get the list of printers from Windows within 20 seconds, which it asks for before it takes each job. A Spooler that is stopped or hung does this. So can one printer that is a connection to a printer shared by another computer (a print server) while that computer is switched off or cannot be reached: Windows opens every such connection each time the printers are listed and waits for it to time out. Jobs for every printer are held up by it, not only jobs for that printer. Bring the print server back, or remove that printer connection from Windows. The print-server case is known from Microsoft's documentation of the Windows call and has not been reproduced on a station. |
| Job remains queued | Check service status, authenticated realtime connection, current user/device authority, server pause/disconnect state, queue approval/exposure and configured capacity. The cloud preview is bounded; inspect server records for the full queue. |
| Realtime connection cannot start | Use the released native printing API 2.3 server and allow outbound WSS upgrades to the configured origin. Inspect the connection/policy error; a legacy native API 1.x server or blocked socket does not enable HTTP polling fallback. |
| CONFIGURATION_REQUIRED | Have the QQQ administrator correct the complete effective policy or upgrade the incompatible client. Limits must fit declared client ceilings; reconnect does not silently lower them. |
| SPOOLED but no output | Check machine Printing Defaults, hardware media/method, pause and paper/label/ribbon conditions. A clear Windows queue or READY status is not proof of physical output. |
| OUTCOME_UNKNOWN | Inspect output and the Windows queue before reprinting. Do not delete the journal or assume failure. |
| PDF clipped or wrong size | Select actual size versus fit deliberately. Match the machine default, advertised media profile or explicit per-job PDF dimensions to the loaded stock; see [Printer media](PRINTER-MEDIA.md). |
| Zebra prints text or blank labels | Confirm ZPL-capable hardware/driver, DPI, stock dimensions and actual printer mode. Inspect the specific document; previously confirmed output does not qualify every format/driver combination. |
| Protected configuration cannot be opened | It belongs to another Windows identity, or the service account changed. Re-enroll through the service after resolving old jobs; do not copy a user-enrolled DPAPI file. |
| Another worker owns the directory | A second copy of the service host (for example a development build started by hand) holds `worker.lock`. Stop it. Only one service may own a given journal/data directory. |
| An install, upgrade or uninstall stops with "A program run as part of the setup did not finish as expected" and rolls back | One of the installer's own steps failed; Windows Installer does not say which or why. For the step that creates or removes the Start menu shortcut, the reason is in the service's activity log, `%ProgramData%\QqqPrintAgent\logs\qqq-print-agent-<date>.log` (open it as an administrator; the folder is still there after an uninstall): look for the error line `[Installer] Branding shortcut operation failed.` and the text after it. A shortcut file that another program holds is not a cause: it is tried for two seconds and then left where it is, with a `[Installer]` warning line that names the file. **An uninstall** fails at this step for three reasons only: it does not run as an elevated administrator, the registry key `HKLM\SOFTWARE\QRunIO\PrintAgent` cannot be written, or the **Print Connectors** folder of the all-users Start menu cannot be listed. **An install, upgrade or repair** also fails when the install folder, the Start menu or the Print Connectors folder has an untrusted owner or lets an ordinary user write; when the companion is missing from the install folder; when a file that is not this product's shortcut already has the shortcut's name (rename or remove that file, or choose another display name); when a file under that name cannot be opened and the registry does not record it as this product's (close the program that holds it and run the installer again); or when Windows' shortcut automation (the `WScript.Shell` object of Windows Script Host) is not available. A verbose installer log (`msiexec /i <msi> /l*v install.log`) names the step as `ApplyBranding` or `RemoveBrandingShortcut`. None of this has been observed in a real installer run yet; it is what the code and Windows Installer's rules give. |
| A shortcut under **Start → Print Connectors** is still there after an uninstall | The uninstall could not open or delete it, usually because another program held the file, and left it where it is rather than fail. The activity log has a `[Installer]` warning with the file name and the kind of failure. The shortcut points at a program that is no longer installed: delete it by hand (as an administrator), or install again under the same display name, which takes the shortcut over. |
| MSI publisher warning | Stable 1.0.1 is signed. Verify the exact official release checksum and Authenticode signature as described in [Installation](INSTALLATION.md). Earlier prereleases may be unsigned. |

## ZPL prints but PDF does not

The paths use different settings: RAW ZPL carries its format instructions, while PDF is rendered through the Windows driver using its default or the requested per-job media. A diagnostic media choice does not rewrite the machine driver's shared configuration; short-label PDF tests send explicit job dimensions. A default that works in a signed-in user's **Printing Preferences** may differ from the defaults used by the Windows service.

For 4 × 6-inch direct-thermal stock with no ribbon, inspect **Printer properties → Advanced → Printing Defaults** for the queue. Use **4.00 × 6.00 inches** and **Thermal Direct**, with the printer's correct DPI; preserve other settings. Other supplies may require different dimensions or Thermal Transfer. Also verify the physical printer's print method and pause/error state. Do not assume Windows READY or an empty queue rules out a hardware problem.

During 0.1.7 acceptance the machine defaults were 4.09 × 2-inch Thermal Transfer. The ZPL label printed, but the PDF did not despite SPOOLED. Correcting the machine defaults and hardware state allowed one fresh reviewed PDF to print fully and correctly; the user confirmed it. No application-code fix was needed. Inspect the existing job/output before retrying to avoid duplicates. See [acceptance evidence](ACCEPTANCE.md).

For a non-security bug, include Windows version, application version, printer model/driver, the stage that failed, job ID and sanitized error text in a [bug report](https://git.kof22.com/QRun-IO/qqq-print-agent/issues). Never attach credentials, enrollment codes, customer PDFs, address labels, journal databases or raw diagnostic archives without reviewing them.

Security issues belong in [private reporting](../SECURITY.md).
